Overshoot's `/chat/completions` is OpenAI-compatible. Everything you already know about request shape, system prompts, streaming, response format, tools — it works.

The piece that's specific to us is **how you reference your video**. When you create a stream, every moment of it becomes addressable by URL. You drop those URLs into a chat message — as `image_url` for a single frame, or `video_url` for a window — and the model sees them as visual context.

## The reference URI

```
ovs://streams/{stream_id}?<anchor>
```

That's it. The `ovs://` scheme is a reference identifier — the server parses out `stream_id` and the query, then resolves frames internally. It's not a URL you fetch. Everything interesting lives in the query string. Set the right query and you can point at:

- the most recent frame,
- a specific frame number,
- an exact wall-clock timestamp,
- the last 5 seconds,
- a 10-second window starting an hour ago,
- a window between two specific frame numbers.

## Single frame — `image_url`

A single frame needs **exactly one** of these query params:

| Param | What it means | Example |
|---|---|---|
| `frame_index` | Lifetime-indexed frame number. `-1` is the most recent, `-2` the one before, etc. | `frame_index=-1` |
| `timestamp_ms` | Absolute stream-clock ms (since `first_frame_at_ms`). | `timestamp_ms=12480` |
| `offset_ms` | Offset from "now". Negative = past. | `offset_ms=-1500` (1.5s ago) |

```json
{
  "type": "image_url",
  "image_url": {
    "url": "ovs://streams/{stream_id}?frame_index=-1"
  }
}
```

<Tip>
  `frame_index=-1` is the cheapest, fastest way to ask "what's happening right now?". One frame, minimum tokens, no decoding work.
</Tip>

### Snapping to nearby frames

A real stream rarely has a frame at the exact millisecond you ask for. When you anchor by `timestamp_ms` or `offset_ms`, the resolver picks the closest available frame. Two optional knobs control how:

| Param | What it does | Default |
|---|---|---|
| `tolerance_ms` | How far the resolver may search for a frame. | `100` |
| `direction` | Which direction to prefer when no exact match exists: `nearest`, `forward`, or `backward`. | `nearest` |

Both are **ignored when you anchor by `frame_index`** — indices already point at exact frames.

```text
?timestamp_ms=12480&tolerance_ms=250&direction=backward
# "find a frame ≤ 12480ms; search up to 250ms back"
```

## A window of frames — `video_url`

A video segment needs a **start anchor** and accepts an **optional end anchor**. If you omit the end, the segment runs to the live edge.

| Start (pick one, required) | End (pick one, optional) |
|---|---|
| `start_frame_index` | `end_frame_index` |
| `start_timestamp_ms` | `end_timestamp_ms` |
| `start_offset_ms` | `end_offset_ms` |

You can mix anchor types — `start_offset_ms=-30000&end_frame_index=523` is fine.

<CodeGroup>

```json Last 5 seconds
{
  "type": "video_url",
  "video_url": {
    "url": "ovs://streams/{stream_id}?start_offset_ms=-5000"
  }
}
```

```json Specific window
{
  "type": "video_url",
  "video_url": {
    "url": "ovs://streams/{stream_id}?start_timestamp_ms=60000&end_timestamp_ms=70000"
  }
}
```

```json Between two frames
{
  "type": "video_url",
  "video_url": {
    "url": "ovs://streams/{stream_id}?start_frame_index=1200&end_frame_index=1500"
  }
}
```

</CodeGroup>

### Subsampling — `max_fps`

A 10-second window at 30 fps is 300 frames. Most of those are redundant. Overshoot subsamples segments to **1 fps by default** so you don't pay for visual tokens that say nothing new.

Override it with `max_fps`:

```text
?start_offset_ms=-3000&max_fps=5
# last 3 seconds, sampled at up to 5 fps → up to 15 frames
```

| Want | Try |
|---|---|
| Cheap "did anything happen?" | `max_fps=1` (default) |
| Smooth motion | `max_fps=5` to `10` |
| Frame-accurate | Don't use `video_url` — pull individual frames by `frame_index`. |

<Warning>
  Visual tokens dominate prompt size. A 30-second `video_url` at `max_fps=10` is ~300 frames — at Qwen 480p that's ~60K tokens before any text.
</Warning>

## Quirks worth knowing

<AccordionGroup>

<Accordion title="Negative indices and offsets are relative to 'now'" icon="arrow-left">
  Negative `frame_index` is interpreted against `last_frame_index` at request time, so `frame_index=-1` always means "most recent". Same for `offset_ms` — it's measured from the live edge when the request lands, not when you wrote the URL.

  This means two requests sent a second apart with `frame_index=-1` see different frames. That's usually what you want.
</Accordion>

<Accordion title="Old frames clamp; future frames fail" icon="scissors">
  Streams retain a rolling buffer. Reference a frame older than `first_available_frame_index` and the resolver clamps up to the oldest available frame — your request **succeeds** on a slightly different frame than you asked for.

  Reference a `frame_index` newer than `last_frame_index` and you get `422`. There is no "wait until that frame arrives" semantics.
</Accordion>

<Accordion title="`tolerance_ms` and `direction` only apply to time-based anchors" icon="filter">
  `frame_index` already names an exact frame — there's nothing to snap to. If you set `tolerance_ms` or `direction` alongside `frame_index`, they're ignored (the resolver emits a warning).
</Accordion>

<Accordion title="Mixing anchor types in one segment is fine" icon="merge">
  `start_offset_ms=-30000&end_frame_index=523` is a valid segment URL. The resolver evaluates each anchor in its own coordinate space, then takes the intersection.
</Accordion>

<Accordion title="The model never fetches the URL itself" icon="server">
  `ovs://` is a reference scheme, not a fetchable URL. The server parses `stream_id` and the query out of it and resolves frames internally; nothing makes an HTTP request to it. The model never sees the URI either — Overshoot rewrites the content parts into resolved frames before forwarding to the model.

  That's the whole reason for `ovs://` — the old `https://api.overshoot.ai/v1beta/streams/{id}/media?...` shape looked fetchable but never was, which confused enough people that we cut it.
</Accordion>

</AccordionGroup>

## Patterns

<CardGroup cols={2}>
  <Card title="What's in front of me right now?" icon="image">
    `image_url` with `frame_index=-1`. One frame, one tokenization, fastest possible answer.
  </Card>
  <Card title="Did anything just happen?" icon="film">
    `video_url` with `start_offset_ms=-3000`. Three seconds back to the live edge, ~3 frames at default fps.
  </Card>
  <Card title="Replay 10:00–10:30" icon="clock">
    `video_url` with `start_timestamp_ms` + `end_timestamp_ms`. Stable across calls, doesn't drift with the live edge.
  </Card>
  <Card title="Compare two cameras" icon="grid">
    Two `image_url` parts in the same `messages` array, each with a different `stream_id`. The model sees them as separate visual contexts.
  </Card>

## Full request

<Accordion title="curl" icon="code">
  ```shellscript wrap
  curl -X POST https://api.overshoot.ai/v1beta/chat/completions \
    -H "Authorization: Bearer $OVERSHOOT_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{
      "model": "google/gemma-4-E4B-it",
      "messages": [{
        "role": "user",
        "content": [
          { "type": "text", "text": "What does it say on my shirt?" },
          { "type": "image_url", "image_url": {
              "url": "ovs://streams/$STREAM_ID?frame_index=-1"
          }}
        ]
      }]
    }'
  ```
</Accordion>

<Accordion title="New to Chat Completions?" icon="circle-question">
  A chat completion request has two essentials:

  - `model` — which model to run.
  - `messages` — a list of `{ role, content }` entries. Roles are `system`, `user`, `assistant`. `content` can be a plain string or a list of typed parts (text, image, video).

  ```json
  {
    "model": "google/gemma-4-E4B-it",
    "messages": [
      { "role": "system", "content": "You are a helpful assistant." },
      { "role": "user",   "content": "What is the capital of France?" }
    ]
  }
  ```

  For vision-language models, image and video parts can carry HTTP URLs or base64 data URIs. Overshoot adds one extra recipe: an HTTPS URL pointing at one of your live streams.
</Accordion>

## URI grammar — full spec

```
ovs://streams/{stream_id}?<query>
```

- Scheme **must** be `ovs://`. Any other scheme (including `https://`) returns `422 stream_url_invalid`.
- Authority **must** be `streams`. The path component **must** be `/{stream_id}` — exactly one segment, the UUID returned by `POST /streams`.
- `ovs://` is a reference identifier the server parses to extract `stream_id` and the query. No HTTP fetch ever happens against this URI; the model resolver looks frames up internally.

### `image_url` query params

Exactly one **anchor** is required:

| Param | Type | Meaning |
|---|---|---|
| `frame_index` | int | Lifetime-indexed frame number. Negative = relative to live edge. `-1` is most recent. |
| `timestamp_ms` | int | Absolute stream-clock ms since `first_frame_at_ms` (the value returned by `GET /streams/{id}`). |
| `offset_ms` | int | Offset from "now" (last frame at request time). Negative = past, positive = future (always fails). |

Optional **modifiers** (ignored when `frame_index` is set):

| Param | Type | Default | Meaning |
|---|---|---|---|
| `tolerance_ms` | int > 0 | `100` | How far the resolver may snap to find a frame. |
| `direction` | enum | `nearest` | `nearest` \| `forward` \| `backward`. Resolution preference when no exact match within tolerance. |

Setting more than one anchor → `422 query_param_invalid`.

### `video_url` query params

Exactly one **start anchor** is required:

| Param | Type | Meaning |
|---|---|---|
| `start_frame_index` | int | Lifetime index. |
| `start_timestamp_ms` | int | Absolute stream-clock ms. |
| `start_offset_ms` | int | Offset from now; negative = past. |

At most one **end anchor** (defaults to live edge if omitted):

| Param | Type | Meaning |
|---|---|---|
| `end_frame_index` | int | Lifetime index. |
| `end_timestamp_ms` | int | Absolute stream-clock ms. |
| `end_offset_ms` | int | Offset from now. |

Optional **subsample**:

| Param | Type | Default | Meaning |
|---|---|---|---|
| `max_fps` | float > 0 | `1.0` | Cap on frames per second sampled from the segment. Lower = cheaper. |

Setting more than one start anchor or more than one end anchor → `422`.

### Resolution semantics

- **Negative `frame_index` / `offset_ms`** are evaluated against `last_frame_index` / now at request time, so the same URL can resolve differently on consecutive calls.
- **Old frames clamp.** A `frame_index` (or `start_frame_index`) older than `first_available_frame_index` clamps up to the oldest available frame. Request succeeds, possibly on a different frame than asked.
- **Future frames fail.** A `frame_index` newer than `last_frame_index` returns `422`. There is no wait-until-arrival.
- **Anchor types may be mixed in one segment.** `start_offset_ms` + `end_frame_index` is valid.
- **Duplicate query keys** (`?frame_index=1&frame_index=2`) → `422`.

### Request shape

```json
{
  "model": "<id from GET /models>",
  "messages": [
    {
      "role": "user",
      "content": [
        { "type": "text", "text": "..." },
        { "type": "image_url", "image_url": { "url": "..." } },
        { "type": "video_url", "video_url": { "url": "..." } }
      ]
    }
  ],
  "max_completion_tokens": 256,
  "response_format": { "type": "text" }
}
```

The endpoint accepts unknown top-level fields and forwards them to the upstream model — anything OpenAI accepts works (including `tools`, `tool_choice`, `temperature`, `seed`).

### Response shape

```json
{
  "id": "...",
  "object": "chat.completion",
  "created": 1777530304,
  "model": "google/gemma-4-E4B-it",
  "choices": [
    {
      "index": 0,
      "message": { "role": "assistant", "content": "..." },
      "finish_reason": "stop"
    }
  ],
  "usage": { "prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0 }
}
```

### Errors

| Code | `error` / `code` | Meaning |
|---|---|---|
| `401` / `403` | — | Missing or invalid API key. |
| `404` | — | `stream_id` doesn't exist or isn't owned by your key. |
| `422` | `stream_url_invalid` | URI scheme isn't `ovs://`, or the path isn't `streams/{id}`. |
| `422` | `query_param_invalid` | Wrong anchor count, unknown query key, malformed value, duplicate key, out-of-range `frame_index`, etc. |
| `422` | `model_not_found` | `model` field doesn't match any entry in `GET /models` (or model is not currently `ready`). |
| `503` | — | No replica is currently serving the requested model. Retry, or list `/models` and fall back. |

### Streaming

Pass `"stream": true` in the request body to receive Server-Sent Events. The chunk shape matches OpenAI's streaming format (`data: {choices: [{delta: {...}}]}\n\n`, terminated by `data: [DONE]`).

### Cost math

```
prompt_tokens ≈ text_tokens + n_frames × tokens_per_frame
```

For Qwen at 480p, `tokens_per_frame ≈ 200`. A `video_url` segment of length `T` seconds at `max_fps=F` produces roughly `min(T × F, T × stream_fps)` frames — the actual frame count caps at the publisher's frame rate.

| Knob | Effect on tokens |
|---|---|
| Halve `max_fps` | Halves frame count, halves visual tokens. |
| Drop publisher resolution 1080p → 480p | Roughly 5× fewer tokens per frame on Qwen. |
| Switch from `video_url` to a single `image_url` | Tokens collapse to one frame's worth. |
